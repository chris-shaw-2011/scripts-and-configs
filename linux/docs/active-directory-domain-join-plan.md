# Active Directory Domain Join Script

## Summary

Add an interactive, idempotent `linux/active-directory.sh` component for Ubuntu 24.04, Ubuntu 26.04, and Debian 13, including Debian 13-based Proxmox VE and Backup Server hosts. It will join the host to one AD domain using `realmd`, `adcli`, and SSSD; restrict Linux login to one AD group; create home directories; grant that group password-protected sudo; and validate PAM-based access for installed login services.

## Interfaces and Workflow

- Support `sudo ./active-directory.sh [--debug]`.
- Run it from `linux/setup.sh` immediately after timezone configuration, since Kerberos depends on correct time.
- On an unjoined host, ask `Configure Active Directory login on this host? [y/N]`; declining safely skips the component.
- Prompt for:
  - AD DNS domain.
  - Join account, defaulting to `Administrator`.
  - Optional computer OU distinguished name.
  - AD group allowed to log in.
  - A representative user in that group for verification.
- Let `realm join` request the join password directly so it is never stored in variables, files, command arguments, or logs.
- Use fully qualified identities such as `user@example.com` and `group@example.com`.
- On rerun:
  - After a successful setup, write a root-owned `0600` completion marker in `/var/lib/active-directory-setup/` (root-owned `0700`). Subsequent runs skip immediately without prompting, verifying, discovering the domain, changing configuration, or restarting services.
  - Write the marker only after every setup and validation step succeeds. Declined or failed setups remain retryable. Previously configured hosts need one successful run of the updated script to create it.
  - Without the marker, follow the existing partial-setup recovery flow below. Deliberately remove the marker to rerun configuration and verification; it is not a domain-health indicator.
  - Validate and reuse an existing compatible SSSD AD join without requesting join credentials.
  - Recover the permitted group from the existing realm configuration where possible.
  - Refuse to overwrite an incompatible realm, multiple-realm setup, or non-SSSD integration.
  - Never automatically leave or rejoin a domain.

## Implementation Changes

- Detect and accept only Ubuntu 24.04, Ubuntu 26.04, or Debian 13 using `/etc/os-release`; fail with the detected platform on unsupported systems. Do not gate compatibility on Proxmox product versions or installed server packages. Retain VE detection only for hostname safety guidance.
- Require an interactive root session, a synchronized clock, and a current FQDN whose suffix matches the requested AD domain.
  - Never change DNS, networking, or hostname automatically.
  - For non-VE hostname failures, print the appropriate `hostnamectl set-hostname host.domain` command and note that DNS and `/etc/hosts` must also resolve it correctly. Establish the permanent hostname before enrollment, including on PBS.
  - For Proxmox VE, explain that the final hostname must be established before cluster creation and must not be changed automatically on a clustered node. Do not apply VE cluster guidance to PBS.
- Install missing packages with the existing helper: `realmd`, `packagekit`, `sssd-ad`, `sssd-tools`, `adcli`, `libnss-sss`, `libpam-sss`, `samba-common-bin`, `krb5-user`, and `sudo`.
  - The shared helper must inspect dpkg installed status, not just successful status-query exit codes. Removed/config-only and incomplete packages require installation; fully installed held packages are accepted without changing their hold.
- Before new enrollment, verify installed package status and disable realmd automatic package installation with `[service] automatic-install = no` in `/etc/realmd.conf`. Preserve unrelated configuration, back up changes, install atomically as root-owned `0600`, start PackageKit, and restart realmd before discovery. PackageKit remains required for installed-package checks even when automatic installation is disabled. Stop on missing dependencies or service startup failure. Existing joins skip this enrollment-only step.
- Validate AD DNS discovery with verbose `realm discover`; stop with resolver diagnostics if AD LDAP/Kerberos records cannot be found.
- Back up existing SSSD, Kerberos, NSS, and the five active common PAM configuration files before the first enrollment. Use explicit paths so earlier backups are not copied again.
- Join explicitly with SSSD and `adcli`, passing the optional computer OU when supplied.
- Add a root-owned `0600` SSSD drop-in for the joined domain that enforces:
  - Fully qualified names.
  - Credential caching.
  - `/home/user@domain` fallback home directories.
  - `/bin/bash` as the fallback shell.
- Reconcile the responder activation generated by `realm join` with the distribution's enabled SSSD socket units:
  - On SSSD 2.10 or newer, remove the obsolete `[sssd] config_file_version` option still generated by realmd 0.17. Preserve it on older SSSD versions and perform this cleanup even if responder sockets are disabled.
  - Remove the `[sssd]` `services` directive only when it contains the standard NSS/PAM realm responders; back up the file and refuse to overwrite customized responder lists.
  - Validate both changes together in a temporary configuration, save one original backup, and install atomically. Leave the original untouched if any unrelated validation error remains. Apply the same cleanup when reusing an existing enrollment.
  - Disable `sssd-pac.socket` while retaining the AD provider's implicit PAC responder, avoiding duplicate PAC processes and failed systemd units.
  - Reset failed state only for existing units; skip absent units such as the private PAM socket removed in newer SSSD releases, while reporting actual inspection or reset errors.
- Restrict host access to the qualified AD group using `realm permit --groups`. This intentionally uses SSSD’s simple access provider: nested AD groups work, but Windows logon-right GPOs are not enforced.
- Enable the packaged `mkhomedir` PAM profile without forcing over locally customized PAM files; restart SSSD and run `sssctl config-check`.
- Add `/etc/sudoers.d/80-ad-domain-admins`, granting the qualified group normal password-protected `ALL=(ALL:ALL) ALL` access. Quote the complete `%group@domain` token so spaces and sudoers metacharacters are safe, validate a temporary file with `visudo`, then install it atomically as root-owned `0440`.
- Do not install or reconfigure OpenSSH, GNOME/GDM, XFCE, XRDP, DNS, NTP, or Proxmox web authentication.
  - Existing PAM-based GDM and XRDP installations inherit SSSD authentication.
  - Preserve the current SSH authentication policy; inspect it and report when password authentication, PAM, `AllowUsers`, or `AllowGroups` prevents domain login.
  - Exclude Proxmox VE/PBS web UI AD realms and backup configuration entirely.

## Validation and Documentation

- Automated tests will cover supported-platform detection, prompt validation, FQDN/domain checks, skip behavior, command construction, optional OU handling, secure password flow, idempotent joined-host behavior, group qualification, sudoers generation, and failure paths using mocked system commands.
- Cover PackageKit installation and startup, configuration preservation and backups, idempotent reruns, installed-status checks, service startup failures, ordering before enrollment, and exclusion of old backups.
- Cover SSSD 2.10 obsolete-option cleanup, older-version preservation, non-socket installations, combined backups, and validation failure preservation.
- Cover secure completion-state creation only after success, no marker after decline or failure, completion of partial existing enrollments, and immediate noninteractive skips with no verification or service changes.
- Run Bash syntax checks across all Linux scripts and tests.
- Post-join checks will require:
  - `realm list` reports the requested SSSD realm and permitted group.
  - SSSD configuration and service health pass.
  - NSS, PAM, and PAC responder units are not failed.
  - `getent passwd`, `id`, and group membership resolve the test user.
  - `sssctl user-checks` passes for `login` and each installed PAM service among `sshd`, `gdm-password`, and `xrdp-sesman`.
  - `visudo` accepts the managed rule and `sudo -l -U` recognizes the test user.
- Document manual acceptance on Ubuntu 24.04, Ubuntu 26.04, and Debian 13, including Proxmox VE 9.2 and Proxmox Backup Server 4.x:
  - Keep the current administrator session open.
  - Test `ssh -l 'user@domain' host` under the existing SSH policy.
  - Test terminal login.
  - Test GDM through “Not listed?”.
  - Test XRDP using `user@domain` and the existing XFCE session.
  - Confirm first-login home creation and password-protected sudo.
- Update `linux/README.md` with prerequisites, prompts, qualified-name examples, configuration files, troubleshooting, completion-marker rerun behavior, and rollback using `realm leave`, removal of the managed sudo/SSSD files and completion marker, and restoration of timestamped backups.
- Do not automatically undo a successful AD enrollment if a later validation step fails; report the partial state and remediation so the AD computer account is not silently mutated.

## Assumptions

- The environment has one directly joined AD domain; trusted-domain and multi-realm policy are outside scope.
- AD-integrated DNS and reliable time synchronization are configured before enrollment.
- The existing host FQDN is the intended permanent AD computer identity.
- The selected AD group is the sole domain login allow-list and also receives password-protected Linux sudo.
- Existing local accounts and root access remain available.
- Actual password authentication and graphical session startup require manual testing; the script can verify identity and PAM account authorization but will not collect the test user’s password.
- Ubuntu 26.04’s unprivileged SSSD service behavior will be respected by using distribution tooling and secure supported configuration locations.
